# Threat model

This hub holds all three parts of the "lethal trifecta":

1. **Private data:** database rows, private repositories.
2. **Untrusted content:** log lines, Sentry error messages, PR bodies and commit messages that anyone can write.
3. **An exfiltration channel:** creating a GitHub issue.

Design as if a log line will one day contain instructions for the model. The table below is the MCP-specific threat model from the blueprint (v2, "MCP-specific threat model"). One test per row is added by week 12 (#11).

"Owning phase" is the roadmap issue that builds the mitigation. "Test" names the test that covers the row today; `—` means no test yet.

## Controls added in Phase 2

- **Tenant isolation:** `createTenantClient` forces `org_id` into every tenant-table query, rejects a foreign `org_id`, nested relations and raw SQL (see `packages/db/src/tenant/`). `organizations` queries are limited to the scope's own row (read and update only; no create or delete). The global `users` and `mcp_clients` tables are rejected on the tenant client; they span every org and need their own repository. Every relation between tenant tables is a composite foreign key on `(org_id, id)`, so the database refuses a row that points at another org's row (for example a `tool_policies` row in org A with org B's `project_id`). A foreign `orgId` inside a compound unique key (such as `orgId_slug`) is rejected, and every `cursor` is pinned to the scope's org. `credentials.store` still checks the integration first, to return "not found".
- **Credential storage:** AES-256-GCM envelope encryption, per-credential data key, `key_version`, AAD `orgId:credentialId` (ADR 0002).
- **Audit trail:** `audit_events` is append-only, enforced by a database trigger on UPDATE, DELETE and TRUNCATE. Every `credentials.reveal` appends a `credential.reveal` event (credential id and outcome, never the value) before the token is returned. The trigger blocks the app's own UPDATE, DELETE and TRUNCATE, but the table's owner role can still disable it, and the app runs as the owner today. Running the app as a non-owner role without `TRIGGER` privilege is planned for the deploy phase. The comment in migration `20261122000100` overstates this and can't be edited, because the migration is already applied.
- **Logs:** Pino with `trace_id` on every line. Fields named `token`, `password`, `authorization`, `cookie`, `set-cookie`, `DATABASE_URL`, `DIRECT_URL` and `HUB_MASTER_KEY` are redacted, and GitHub (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), Sentry (`sntrys_`, `sntryu_`), Bearer and Postgres-URL secrets are scrubbed from strings in the logged object, the message and errors, including their `cause` (`apps/server/src/redact.ts`). The finished JSON line is scrubbed again just before it is written, which covers class instances such as Fastify's `req` (so a token in `req.url` is hidden), child-logger bindings and object keys; the object walk is capped at depth 10. Vercel tokens and older unprefixed Sentry tokens are caught by field name only.
